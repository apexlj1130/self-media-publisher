# 自媒体双平台发布 Skill 技术架构设计

修订日期：2026-09-17

## 1. 架构结论

采用“一个 Skill 编排层 + 一个统一内容准备器 + 两个平台适配器”的单 Agent Loop：

```text
原始 Markdown
      ↓
统一内容包 + 源指纹
      ├── 微信适配器：官方 API → 草稿箱 → 回读核验
      └── 小红书适配器：包校验 → 可见 Chrome → 页面复核
                         ↓
                 分平台确认与发布闸门
```

不引入常驻 MCP、LangGraph、Deep Agents、自定义状态数据库或多 Agent。两个平台是工具和权限不同的适配器，不是独立规划 Agent。

## 3. 模块边界

### 3.1 Skill 编排层

负责平台选择、语义改编、调用 `imagegen`、组织运行包、选择平台适配器、真实页面复核和向用户请求确认。它不保存凭证，也不把脚本输出当成语义正确性的证明。

### 3.2 统一内容准备器

`prepare_content.py` 从 Markdown 生成 schema v2 内容包和微信暂存 HTML。它只做确定性解析、候选语义锚点和基础样式，不访问网络、不调用图片工具、不创建草稿。

### 3.3 媒体清单校验器

`validate_media_manifest.py` 验证源指纹、双平台图片键、绝对路径、文件存在性和平台顺序。它不判断图片审美或语义质量。

### 3.4 微信 API 适配器

`wechat_draft.py` 重新实现并收敛 `jiji262/wechat-publisher` 已验证的官方 API 路线：

- 读取单账号 YAML 配置；
- 获取并以 0600 权限缓存 access token；
- 上传封面和正文图片；
- 将语义图片标记替换为微信 CDN 图片；
- 创建普通图文草稿；
- 回读草稿并输出不含凭证的结果收据。

网络层通过可注入 transport 测试；只有 5xx、连接失败或超时可以有限重试。微信应用层错误、尤其 `40164`，直接失败。

### 3.5 小红书包校验与 Computer Use

`validate_xhs_package.py` 只验证发布包的客观约束。真实发布动作由 Codex Computer Use 操作可见 Chrome，不安装上游 XHS Bridge，不读取 Cookie，不执行页面脚本。

小红书适配器没有“一步发布”命令。浏览器安全策略、验证码或风险提示是硬停止条件。

## 4. 数据契约

### 4.1 统一内容包

```json
{
  "schema_version": 2,
  "source_sha256": "...",
  "default_platforms": ["wechat", "xiaohongshu"],
  "title": "原始标题",
  "body_markdown": "正文",
  "images": [],
  "layout_instructions": [],
  "publish_options": {"declare_original": true}
}
```

### 4.2 媒体清单

```json
{
  "schema_version": 1,
  "source_sha256": "...",
  "wechat": {"image-01": "/abs/cover.png", "image-02": "/abs/body.png"},
  "xiaohongshu": ["/abs/cover.png", "/abs/card-01.png"]
}
```

### 4.3 小红书发布包

```json
{
  "schema_version": 1,
  "source_sha256": "...",
  "title": "小红书标题",
  "content": "正文",
  "tags": ["AI", "Agent"],
  "images": ["/abs/cover.png", "/abs/card-01.png"],
  "visibility": "公开可见",
  "declare_original": true
}
```

## 5. 状态、确认与幂等性

内容指纹由原始素材、平台内容、图片清单和发布选项共同计算。确认收据以平台为键：

```json
{
  "wechat": {"fingerprint": "...", "confirmed": true},
  "xiaohongshu": {"fingerprint": "...", "confirmed": false}
}
```

该结构用于当前任务中的比较，不作为长期数据库。脚本不能自行把 `confirmed` 设为真；用户消息才是授权来源。

微信创建草稿返回 `media_id` 后立即回读。小红书点击发布后读取成功页面或发布记录。未知状态不得重复提交。

## 6. 安全边界

- 微信凭证文件位于 Skill 和 Git 之外，权限必须为 0600。
- token 缓存只包含账号键、不可逆凭证指纹、token 和到期时间，权限为 0600，不输出到日志；app_id 或 app_secret 变化会让旧缓存失效。
- 小红书使用专用可见 Chrome Profile；不保存密码、验证码或 Cookie。
- 不使用 Headless、私有 API、Cookie 导出、token 抓取、UA/指纹伪装、CDP、Shadow DOM 穿透或脚本发布事件。
- 浏览器策略拒绝即停止，不切换实现绕过。
- 所有图片由 Codex `imagegen` 产生，程序只校验文件与契约。

## 7. 开源复用边界

- 微信：沿用 `jiji262/wechat-publisher` 的官方 API 接口边界、错误经验和移动端列表修复；在本 Skill 中以测试先行重新实现最小代码，并记录 MIT 声明与来源。
- 小红书：借鉴 `autoclaw-cc/xiaohongshu-skills` 的 fill/preview/confirm 流程和 MIT 许可，但不复制或安装其高权限 Chrome 扩展。
- `tensorslab/xhs-skills` 只作为内容卡片规划参考；不采用 HTML/CSS 卡片渲染。

## 8. Agent 能力所有权

| 关注点 | 权威所有者 | 证据 |
|---|---|---|
| 规划与语义改编 | 当前主 Agent | 原稿、平台要求和页面观察 |
| 确定性解析与校验 | 本地脚本 | 单元测试与退出码 |
| 图片质量 | 当前主 Agent | `imagegen` 结果与视觉复核 |
| 微信草稿写入 | 微信官方 API | `media_id` 与草稿回读 |
| 小红书页面操作 | Computer Use | 可见页面状态 |
| 登录与验证 | 用户与平台 | 扫码、验证码、实名状态 |
| 发布授权 | 用户 | 当前平台内容指纹对应的明确确认 |
| 完成判定 | 主 Agent，受平台证据约束 | 草稿或发布状态回读 |

最简单但被拒绝的方案是把两个上游项目原样放进同一目录：它会带来重复编排、过宽浏览器权限、外部生图后端和不一致的确认规则。更复杂的图工作流也被拒绝，因为顺序发布和局部重试可以由单 Agent Loop 与确定性收据处理。

## 9. 验证策略

1. 先写内容包、媒体清单、小红书包和微信 API 的失败测试。
2. 聚焦测试逐个通过后运行完整离线套件。
3. 扫描候选包，确认无凭证、token、Cookie、真实原稿或运行产物。
4. 使用官方 Skill 校验器验证源码、归档和安装副本。
5. 真实验收分阶段授权：先微信 API 草稿，再小红书保存草稿；任何正式发布需要当前草稿确认。

## 10. 实现后架构复核

复核日期：2026-09-17

- 实现保持单一 Codex Agent Loop，没有引入常驻 MCP、LangGraph、Deep Agents、子代理或第二规划器。
- 统一准备器和两个校验器只处理可确定验证的结构、指纹和路径，不把结构化输出当作语义正确性或用户授权。
- 微信 API 适配器是独立深模块：配置、token、上传、草稿创建和回读位于同一安全边界；没有把凭证或网络状态泄露给 Skill 编排层。
- token 和只读草稿回读允许有限瞬时重试；永久素材上传和 `draft/add` 不自动重试未知结果，避免重复副作用。
- 小红书只有发布包校验器和可见 Chrome 操作说明，没有私有 API、Cookie、CDP、页面脚本或高权限扩展实现。
- 分平台确认由当前用户消息提供，代码和运行包不能自行生成有效确认。
- 主 Agent 代码审查发现并修正两项边界问题：凭证重置后旧 token 缓存复用，以及私有 JSON 写入器修改既有父目录权限。两项均有先失败后通过的回归测试。
- 由于用户明确禁止子代理，审查不是独立模型评估；27 个确定性测试、官方 Skill 校验、配置值扫描、干净归档和安装副本复验提供独立于模型自述的证据。

实现与批准架构无方向偏离。真实平台草稿和页面交互仍保留为需要当次授权的在线验收，不以离线结果冒充。
